# AGENTS.md
- Administrative physical deletion uses guarded parent-table DELETE triggers and SQL-editor-only atomic functions with ID plus email confirmation; contract decisions, consents, assignments, offers linked to drivers, billing evidence and files block deletion pending retention review. A user-confirmed test record may be removed only through a same-migration exception hard-guarded to fixed record and profile IDs plus a session confirmation flag, with the original protections restored and re-tested in that same migration. Why: preserves immutable evidence and auth while removing only unencumbered or explicitly confirmed test records without storage or email side effects.

- The admin contract-invitation overview reads paginated invitation rows joined to driver profiles through the existing foreign key, omits tokens and opens the existing driver-data dialog; invitation state is not a contractual decision. Why: administrators can identify and search every invitation without new write paths or disclosure of private links.


- Overnight-cost copy has matching frontend and function-local text modules and a shared customer/admin email notice selected by tariff key before legacy flags. Why: keeps approved wording consistent without coupling Edge Functions to frontend files or changing tariff calculations.

- All existing sitemap URLs are prerendered after `vite build` by `scripts/prerender.mjs` into `dist/prerender/<route>.html`, with `/` in `prerender/index.html`; the sitemap is the authoritative route list. Why: every indexed page gets full HTTP HTML without route-named directories or changes to the SPA fallback template.
- The prerender step must fail the build (exit 1) when it cannot produce every page. Why: a production upload must never ship landing pages that are only `<div id="root"></div>`.
- Prerendered HTML reuses the built `index.html` head unchanged (tracking snippets exactly once) and only swaps in the useSEO-managed tags and the `#root` markup. Why: avoids duplicate tracking and keeps the head identical to the SPA.
- Both public Apache configurations must be byte-identical; the IONOS packaging script copies the authoritative configuration and validates the final prerender directory without regenerating rewrite rules. Why: packaging must not discard prerender routing or reintroduce internal redirect loops.
- Whole-job cancellation is handled only by the authenticated admin-cancel-job function, with a conditional status claim, assignment cancellation and final parent status readback before mail. Why: separates it from assignment dissolution and prevents duplicate clicks or assignment transitions from sending premature cancellations.
- Cancellation recipient policy and text generation live in the function-local cancellation module with injected delivery dependencies. Why: eligibility and duplicate suppression can be tested without production data or real email.
- Admin assignment confirmation and the driver's binding acceptance are separate records: only a `job_driver_acceptances` row with `flow='binding'` (immutable via trigger, one per assignment) counts as binding driver acceptance; binding links are `assignment_invites` rows with `purpose='binding'`. Why: an admin selection must never be presented or evidenced as the driver's contractual acceptance.
- Binding-acceptance contract text lives in matching frontend and function-local modules (`driverContractTerms`), checked equal by a test. Why: the text shown, stored, mailed and put in the PDF must be identical.
- Assignment start/end are entered as calendar dates only (no time) and stored as UTC day starts; all display (mails, acceptance page, evidence, PDF) formats only via the identical modules `src/lib/berlinTime.ts` / `supabase/functions/_shared/berlin-time.ts` (equality tested). `job_assignments.times_entered=true` marks rows with real times (kept unchanged, shown with time); NULL marks date-only rows, shown date-only and never used as a time-based deadline. Why: daily working times are agreed between customer and driver; no time may be invented, and display must be identical everywhere.
- The booking-form cost preview and accommodation options live in the identical module pair `src/lib/kostenUebersicht.ts` / `supabase/functions/_shared/kosten-uebersicht.ts` (equality tested); the server recomputes the estimate and stores it as a `job_requests.kosten_uebersicht` snapshot. Why: the customer must see the same figures in the form and the confirmation email, and client-sent prices are never authoritative.
- Accommodation ceiling parsing (`parseUnterkunftObergrenze`) lives in the kostenUebersicht module pair and is used by both the form and `submit-fahrer-anfrage` (re-exported function-locally), with regression tests. Why: the form must never accept a value the server rejects.
- Job release is one shared server rule (`_shared/job-release.ts`): only jobs with `approved_at` set by the admin's explicit release and a still-releasable status may be offered to drivers; every sending function and `respond-invite` (which also rejects blocked/inactive drivers) checks it server-side. Why: driver approval or UI buttons must never bypass the admin release.
- Test sends (`send-test-job-invite`) are preview-only and never create invites; unreleased jobs may only go to the internal test address (`test-send-policy.ts`). Driver-approval job selection lives in the pure `approve-driver-and-send-jobs/matching.ts` with sample-data tests. Why: tests must never create real acceptances, and matching must be verifiable without DB or email.
- The driver mediation contract lives in the identical module pair `src/lib/driverMediationContract.ts` / `supabase/functions/_shared/driver-mediation-contract.ts` (equality tested); decisions are stored only by the `driver-contract` function in immutable `driver_contract_decisions` rows, and the offer/approval gate is behind `feature_flags.driver_contract_required`. Why: the text shown and evidenced must be identical, and the existing operation stays unchanged until the cut-off switch is turned on.
